# Lean 4 formal verification prototype (NOT a published release)

This is a deliberately narrow formal companion to the finite-interface fixture in
`docs/INFINITE_INTERFACE_REPORT.md` and the verifier/authority principle.

## Pinned toolchain

Lean 4.35.0; build from this directory:

```sh
lake build
lake check
```

GitHub CI runs the same commands. Do not report this as "Lean verified" until CI
has passed with no admitted holes, unapproved axioms, or skipped checks.

## Proven obligations (conditional on kernel-accepted build)

1. `quotient_commutes`: for **all** worlds in the published infinite-fibre
   deterministic fixture, taking a world transition then quotienting equals
   quotienting then taking the 4-state macro transition.
2. `every_fibre_is_unbounded`: each of the four macro labels has concrete
   witnesses with arbitrarily high nuisance values.
3. `coarse_task_is_not_dynamically_closed`: an explicit counterexample shows
   that the immediate `a` task does not determine next-task behaviour.
4. `stale_version_rejected` and `rejected_candidate_unchanged`: the abstract
   gate forbids old-spec or noncompliant proposals from altering trusted state.
5. `gate_preserves_compliance`: compliant trusted state remains compliant
   under the fixed-version admission rule.

## Trust boundary and remaining work

- The proof checker verifies propositions **as formalised**, not that their
  meaning adequately captures reality or the Python implementation.
- The `valid` predicate is treated as an externally defined policy oracle.
  Formally deriving this predicate from a versioned DSL and connecting it to
  Python acceptance are separate, currently **unimplemented** obligations.
- These Lean results do **not** formalise the anytime-valid statistical
  confidence bound, approximate stochastic aggregation, the trained policy,
  adaptive history-program search, or all versions of PRIME.
- "Proof generated by an LLM" is a *proposal*. Only kernel-accepted proofs
  under the pinned definitions and allowed axioms can be used as certificates.
- A specification change must mint a new version, invalidate proof bindings
  to the old version, and demand rechecking under the new rules. A model may
  propose revisions; a separate governance policy must authorise them.
- An implementable bridge needs canonical statement, policy/version, input,
  implementation and theorem-hash bindings, timeout/sandbox boundaries,
  verified return codes and tamper/failure tests.

## Suggested empirical release checklist

Freeze code, proofs, Lean toolchain, dependency lock, inputs, evidence protocols,
results and output hashes. Run Python tests and historical replays independently
of formal checking. Include negative controls (bad versions, mismatched specs,
malformed proof objects, false theorem statements) and publish all failures.

The original `v0.7.0` release is not retroactively claimed to be Lean verified.
